# 2026-09-13 -- Direct neural rendering: route A was reachable all along

## What this settles

The two M3 spikes ([2026-08-30](2026-08-30-ngx-feature-probe.md),
[2026-08-31](2026-08-31-reshade-detour.md)) concluded that the neural
rendering runtime could only be driven through the NGX core, and that the
sidecar therefore had to host ReShade and a third-party add-on that detours
the core. Route B shipped on that basis.

That conclusion was wrong in one specific, fixable way. `nvngx_dlssnr.dll`'s
exports answer `FAIL_PlatformError` before inspecting any argument when the
**path of the module that owns the caller's return address does not contain
"nvngx.dll"**. The driver core is `_nvngx.dll`, so it passes by name; the
sidecar, ReShade and every add-on fail by name. Nothing else about the caller
is checked.

The finding is the OptiScaler neural-rendering fork's
(github.com/Dagherbou/OptiScaler_DLSSNR, which ships a 12 KB forwarder named
`nvngx.dll_dlssnr.dll` for exactly this reason). That project is GPL-3; this
one is MIT, so nothing from it is used here. The forwarder and the pass in
this repository are written fresh against the facts below.

## The facts route A rests on

1. **Caller gate.** Calls into the runtime must originate from a module whose
   path contains `nvngx.dll`. Ours is `nvngx.dll_sidecar.dll`
   (`src/forwarder/`). Every call must *return through* that module: a tail
   call (`return fn(...)`) is compiled to a jump, the forwarder's frame
   vanishes, and the runtime resolves the caller past it. Results are parked
   in a `volatile` before being returned.

2. **Parameter block.** The runtime wants the driver core's own capability
   block (`NVSDK_NGX_D3D12_GetCapabilityParameters`), not a block from
   `AllocateParameters`: the core's block carries the snippet and preset
   callbacks a feature expects at create time. `NgxSession` now exposes it.

3. **Init.** The runtime's own `NVSDK_NGX_D3D12_Init_Ext(appId, dataPath,
   device, 0x15, params)` is called through the forwarder, after the core is
   up. Two application ids are tried: this project's, then the generic one the
   OptiScaler fork found the runtime accepts for unregistered callers.

4. **Float setter slot.** The driver's block does not keep its float setter at
   vtable slot 1 where the public header declares it; writes there read back
   as unsupported while every uint lands. The forwarder finds the real slot
   by round-tripping 0.375 through each candidate and reading it back through
   the header's float getter (slot 9). Resources go through the 64-bit setter
   (slot 0), not the typed `ID3D12Resource*` one.

5. **Feature 18.** `CreateFeature(cl, 18, params, &handle)` with
   `DLSSNR.Enabled/Width/Height`, `CreationNodeMask`, `VisibilityNodeMask`
   and the tuning keys set. The model reads its tuning **at create**; values
   written only at evaluate are ignored. A different tuning is a different
   feature, which is why multipass is one feature per pass.

6. **Evaluate.** `EvaluateFeature(cl, handle, params, nullptr)` with
   `DLSSNR.Color/Depth/MVec/Output` as resources, the four subrects,
   `DLSSNR.Width/Height`, `DepthInverted`, `Reset`, `MVecScaleX/Y`, and the
   tuning restated (the block is shared, and whatever else uses NGX in the
   process may have overwritten it). Colour and output are RGBA16F; guides
   rest in `NON_PIXEL_SHADER_RESOURCE`, output in `UNORDERED_ACCESS`.

7. **Create and first evaluate never share a command list.** The feature's
   initialisation work is recorded into the list it is created on, and the
   runtime has been seen to hang the GPU when create and evaluate ride the
   same submission. `DirectNrPass` creates on one frame and evaluates from the
   next.

8. **Driver.** The Sep 2 Krish add-on (v4.7) faults inside the runtime on
   616.64 because of *its* inline-execution design, not the driver: the Aug 28
   build runs on 616.64, and the OptiScaler fork ships against 616.56+. No
   rollback is needed.

## What changed

- `src/forwarder/` -- the forwarder and its C ABI header. Built as
  `nvngx.dll_sidecar.dll`, copied beside `wowsidecar.exe`, and checked by
  `ci/check_imports.py` like every other binary in the project.
- `neural/NrForwarder` -- the host's loader for it, every call SEH-guarded.
- `neural/DirectNrPass` -- the pass. Multipass by ping-pong through RGBA16F
  intermediates, one feature per pass, synthetic depth as before, NVOF motion
  as before. A fault inside the runtime returns `false` so the pipeline
  discards the list unsubmitted and rebuilds on passthrough.
- `Config` -- `[nr]` base tuning and `[[nr.pass]]` overrides. `"direct"` is
  the default `neural_pass`; `"ngx"` is an alias for it; `"reshade"` stays.
- Manager -- presets on the direct route, a per-pass tuning section, a probe
  for the forwarder. ReShade and the add-on are optional components now.

## Still open

- Whether the first application id is accepted, or the fallback is what
  works. The log says which.
- Whether `UseAutoMask` covers WoW's UI well enough to retire the hand-drawn
  mask rectangles. Try it before building a calibrator.
- Real depth, and the 75 % working-resolution path from the OptiScaler and
  RHI work. Both are cheaper to add now that the pass is ours.
- Presenting in scRGB, which opts the overlay out of Auto HDR / RTX HDR and
  is the proper fix for the brightness boost seen on an HDR desktop.
